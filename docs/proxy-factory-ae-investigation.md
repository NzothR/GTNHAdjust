# 代理联合工厂 AE 接入考察

本文记录基于本地参考源码的静态考察，目标环境为 GTNH 2.9.0、AE2 rv3-beta-1095 和 GTNR 0.1.34。参考源码与实际依赖包的具体方法、注入点及其他模组 Mixin 的兼容性仍需在实现时逐项核对；本记录不代表内部流转已经实现。

## 当前阶段

主机作为独立 AE 节点接入网络，输入总成仍负责样板注册和接收。启用 `proxyFactory.directAeOutput` 后，独立线程账本将实际产物直接注入 AE、保存未接收余量并重试，输出仓可选；关闭时沿用输出仓。当前不追踪 CPU 任务身份，也没有实现同机中间物料直通。

## 已定位的路径

- `CraftingCPUCluster.executeCrafting` 按 CPU 的任务、材料可用性、能源及剩余操作次数选择并调用 `ICraftingMedium.pushPattern`；成功后扣除操作次数并将样板产物加入 `waitingFor`。同一配方可能有多个 medium，也存在 GTNR 对批量下发的 Mixin，不能仅凭配方判断实际机器或下发次数。
- `SuperMTEHatchCraftingInputME.pushPattern` 是 GTNR 合成输入总成接收样板与材料的入口。GT 普通 ME 合成输入总成也需单独核对。原接口没有显式传入 CPU 或任务身份，需要在 CPU 下发事务边界关联，并核对失败回滚、批量和同一工厂多个总成。
- CPU 的 `injectItems` 对匹配 `waitingFor` 的实际产物更新进度，将非最终产物放入 CPU 内部库存；最终产物经链接处理。非样板产物和超额部分沿正常网络输出。仅绕过库存写入会使 `canCraft` 和后续提取看不到材料，必须同时适配 CPU 查询、提取及回滚，且不能自行决定下游配方。
- CPU `canCraft`、`executeCrafting` 的材料提取和 `pushPattern` 接受/拒绝是联合事务边界。物料留在工厂时，CPU 仍需以正确的任务归属参与可用性判断；如果最终选择的 medium 不属于同一工厂，必须回退至正常 CPU 路径，避免把其他机器所需物料锁在本机。
- GTNR `RecipeThreadOutputs` 在每个线程中保存大整数产物账本，完成后按切片模拟、提交物品与流体输出，并将余量写入 NBT。未来应基于实际运行包核对是否能在这一边界添加主机输出和任务归属；必须处理部分接收、断网、无空间、崩溃重载与重复提交，不能依赖非原子的模拟结果。
- `CraftingCPUCluster` 保存任务、等待产物、内部库存和合成链接；`getLastCraftingLink` 及链接的 crafting ID 是值得进一步核对的身份线索，但不能仅凭其名称推断任务跨重载、取消、合并或换网时的唯一性。需要针对这些生命周期验证稳定标识和恢复协议。

## 实现前需要验证

需要覆盖多个 CPU、多个并发订单、同种物料的不同归属、相同样板的多个 medium、任务合并和取消、替代材料、物品 NBT、流体、额外和概率产物、GTNR 批量下发，以及服务端保存重载和网络拓扑变化。结构不成型时保留已接收材料；计划取消或确认失效时安全退回原网络，网络不可用或存储不足时持久化等待。主机破坏后内部记录随主机消失。为避免跨网络错误投递，网络身份无法确认时不能猜测归属。

新增 CPU Mixin 和独立流转功能必须有启动时开关；关闭时不加载对应 Mixin。实现时应同步 README、兼容版本和重启说明，并使用默认关闭的诊断日志。游戏内测试由用户进行。

## 测试日志与追踪

2026-11-08 客户端测试日志中，多个线程完成并向 AE 交付产物，日志中的剩余数量为零；这只能验证该次直接输出，不能证明断网恢复、多个 CPU 或内部直通正确。GTNR 的批量下发会把同一批材料写入合成输入总成的样板槽，工厂调度再从该槽取料；单个线程账本目前没有 CPU、合成链接或下发批次。不同 CPU 的相同样板材料可能在槽内合并，因此不能根据产物类型、当前网络或样板猜测归属。

`proxyDispatchDiagnostics` 为默认关闭、只读的 CPU 下发诊断 Mixin。记录实际接收者、链接 ID、批次和材料，有助于核查 GTNR 批量包装与 AE CPU 的实际调用次序；CPU 运行期标识仅用于同一次运行内关联，不能作为跨重启身份。
