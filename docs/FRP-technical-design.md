# FRP 技术设计与实施计划

本文以 [功能设计 v1.1](FRP.md) 为需求基准，并采纳后续约定：机器外壳配方的展示可以在世界加载时按状态确定，状态变化后提示重启生效。本文是开发设计，不代表功能已经实现。目标为 GTNH 2.9.0；参考源码仅供调查，实际实现前必须与整合包对应版本和运行时注册结果核对。

## 1. 工程边界

`frp/` 是独立 Gradle 构建和独立 Forge 模组，ID 为 `futureresourceprotocol`，包名为 `com.futureresourceprotocol`，不引用主模组类、配置、资源或产物。两个 jar 可分别安装，也可共同安装。实际功能需依赖 GTNH 对应的 Forge、GT、AE2 等；逐阶段声明并锁定与 2.9.0 一致的版本，不将参考 jar 打包进产物。FRP 使用自己的配置、世界数据名、网络消息、注册名与资源域；这些名称发布后视为存档兼容接口。主项目仍保持其单模组、已有 ID 和存档兼容性。

预留包：`protocol`（纯业务与事务）、`persistence`（世界数据与迁移）、`recipe`（资格索引及受控配方）、`device`（便携设备与清算终端）、`integration.ae2`、`network`、`command` 和 `mixins`。适配层只调用协议服务，不直接改账本。仅按实际需要引入 Mixin，各功能有启动开关，关闭时不加载对应 Mixin；独立功能也有开关，默认关闭详细诊断。未来文档须说明关闭已有功能对存档的影响，不能以关闭开关删除或重置债务。

## 2. 调查依据与边界

本次只读检查了仓库 `ref/`：AE2 `44b5a5a` 的 `appeng.api.storage.ICellHandler`、`IMEInventory`、`me.storage.CreativeCellInventory`、`tile.storage.TileDrive`；GT `4c7db46` 的 `gregtech.api.recipe.RecipeMap`、`RecipeMapBackend`、`GTRecipe` 和 `PowerGogglesWorldSavedData`；以及 GTNR `3428127` 和 GTNH Core 的机器、配方代码。参考仓库 HEAD 不保证对应 2.9.0，特别是 AE2 API 可能存在版本差异；实现前必须用实例 jar、版本清单和必要的反编译核对，不能将本次发现当作已验证兼容结论。

已发现：GT 的 `RecipeMap.getAllRecipes()` 和 `GTRecipe.mOutputs/mEUt/mEnabled/mFakeRecipe` 可作为静态 GT 配方索引的候选来源，不能据此假设动态配方都可枚举。AE2 的 `ICellHandler` 创建库存处理器，`IMEInventory.extractItems` 区分模拟与实际操作；参考创造元件的 `injectItems` 会吞入匹配物品，FRP 必须实现拒绝注入，不能直接继承其语义。`ICellHandler` 的 host 允许为 null，库存也可能脱离驱动器被查询，因此不能假设所有调用都有世界或网络上下文。GT 中有主世界 `WorldSavedData` 及 `markDirty()` 的先例。

## 3. 世界状态与权限

服务端通过主世界的 `WorldSavedData` 加载唯一权威账本，跨维度始终指向同一个主世界；不使用客户端或静态全局单例作为存档身份。服务关闭、切换世界时清理运行时引用，集成服重进不同存档不得复用旧状态。数据包含 schema 版本、里程碑、终止状态、分类缓存、逐资源逐阶段的累计预支/结算和未清偿量、必要的待返还记录；变更后 `markDirty()`。NBT 保存资源注册名与 meta，不保存运行时数字 ID；缺失模组时保留无法解析的条目，禁止静默清除或错误抵扣。未知新版本或损坏数据应拒绝危险写入并明确报错，迁移需测试并先备份。

债务键为注册名 + meta，忽略 NBT；设备标记键为注册名 + meta + 完整 NBT，限制 900 个、完全相同拒绝。历史累计与余额使用非负 `long` 并做溢出前检查，拒绝无法安全记账的操作，不允许回绕；AE2 的虚拟显示数量只是展示，与账本上限无关。可进一步考虑 BigInteger，但必须在存档格式定稿前决定。

初始允许 UHV 类；UHV 里程碑要求 UHV 债务清零并消耗一个外壳，永久开放 UMV 类；UMV 里程碑要求两类债务均为零并经确认后消耗外壳、永久终止预支。UMV 里程碑是否必须显式要求已完成 UHV 里程碑，功能稿未明确，正常路径预计如此，实施前需确定。结算先抵 UHV 再抵 UMV；阶段覆盖只作用于新债务，同一资源可同时保有两阶段余额。分类缓存首次成功预支时写入；覆盖配置变化不能改写历史条目，缓存与未来覆盖之间优先关系需在实现前明确并写入配置说明。

所有修改仅在服务端主线程串行执行；网络请求须调度到主线程并重验设备位置、持有物、距离、权限、容量和操作对象。核心提供 `canMark`、`quoteAdvance`、`commitAdvance`、`settle`、`submitMilestone` 等明确入口，适配器不绕过权限。资源、账目、里程碑与待返还记录的更新必须验证非负、不超额、无溢出。客户端仅显示服务端快照；变更通知打开的界面，重连重新获取，消息不可作为授权依据。

## 4. 生产资格与分类

在配方注册完成后构建可扩展的产物索引：工作台 `CraftingManager`、熔炉 `FurnaceRecipes`、GT 已知配方池分别作为适配器，登记每个有效主产物和可识别副产物，过滤禁用与展示假配方，并保留来源、稳定排序键和可信电压。各适配器明确标明能否完整枚举；空索引不能证明所有模组没有生产方式。未知或未支持的来源默认拒绝，可用配置显式补充资格；UHV/UMV/UXV 指定外壳在所有入口无条件拒绝。

首次成功预支前依稳定顺序寻找第一条有效电压，低于 UHV 或无有效电压归 UHV，否则 UMV。工作台、熔炉的无电压结果不能阻止查找后续有效 GT 电压。固定排序规则应包含来源优先级、配方池注册名和配方内容的稳定指纹；去重和碰撞处理须确定，不依赖 HashMap 迭代顺序。`mEUt` 的含义、生成类/负值、超限、GTNR 加速对分类的影响，以及特殊动态后端、副产物概率和 wildcard meta 均须按 2.9.0 核验；不明值作为无有效电压，不猜测。为索引设置统计及默认关闭的诊断，注册生命周期和配方变更时何时重建须验证。

## 5. 交付和清算事务

便携终端由服务端先计算可交付数量，再在同一次主线程操作中交付并登记实际数量；客户端的槽位请求不能直接创建物品。处理背包部分接收、光标和 shift 操作，设备移动或替换后拒绝过期请求。操作前检查账本容量及权限，提交不允许抛出可预见异常；对异常和跨存档崩溃不得宣称已获得原子性，需要故障注入验证并设计恢复。

手动清算只消耗能抵扣的数量，超额保留，按实际消耗量结算。AE2 清算以确定顺序逐条、分批处理，记录该资源的预支事件序号；`SIMULATE` 不记账，真实提取后检查序号，正常才抵扣。发现同一资源新增预支时中止整个批次，已成功结算的不回滚，当前未结算提取物进入持久化待返还区，通过发起网络的正常注入返还，部分失败保存余量并可重试，不能以此抵债或撤销新债。不得为避免循环而假设 AE2 优先选择普通库存。不同 NBT 的资源按债务键结算，但每个实际提取物及返还记录须保留原 NBT。

世界数据、方块和 AE2 网络分别保存，`markDirty()` 不是同步磁盘事务；突然崩溃时不能保证跨对象恰好一次。实现前应设计持久化 escrow 的状态转换、保存顺序与可恢复操作，并用重启和故障注入验证；如果底层无法保证，须明确实际边界，禁止以「绝不丢失/复制」作为未验证的承诺。返还区的归属、方块破坏/区块卸载、网络变更、服务器异常关闭以及管理员修复路径须单独实现和测试。

## 6. AE2 接入

注册 FRP 专用存储元件和 `ICellHandler`，物品 NBT 保存标记，处理器只接受物品通道；拒绝所有注入并返回完整未接收物，避免创造元件的吞物行为。查询只报告当前权限允许的标记，实际提取逐次重验权限和完整标记；模拟只返回可交付结果，不修改分类缓存、事件序号或账本。实际提取按处理器真正返回的数量提交债务；普通存储来源不参与记账，遵循 AE2 原本优先级。

世界上下文是关键技术风险：handler 的 host 可为 null，`BaseActionSource` 也不保证总能提供可靠世界；需要原型确认驱动器/箱子和自动化调用链可获得服务端世界与网络身份，拿不到上下文时安全拒绝实际提取，不能使用跨世界静态状态。核查 I/O Port、存储总线、ME 箱、合成和第三方存储适配器是否可绕过。权限变更时按实际可用接口通知已加载相关网络刷新（参考 `MENetworkCellArrayUpdate` 和存储变更通知），卸载后重新加载时重新计算；刷新失败时提取仍须拒绝。网络缓存、优先级、多个磁盘、跨网络及内存泄漏都需要实测。

## 7. 外壳限制与重启语义

世界实际状态是唯一授权来源：UHV 外壳要求 UHV 债务为零；UMV 要求两类均为零；UXV 要求 UMV 里程碑完成。允许配方展示以世界加载时快照静态确定；清算或里程碑导致解锁时标记「需要重启」，重启前继续保持较严格的旧展示及限制。反向变化必须安全：启动后产生新债务时服务端立即拒绝相关工作台和机器实际生产，旧展示可能暂时过期，明确提示需重启以更新展示。启动快照与当前权限取更严格的一方，不能让新债务利用已解锁的旧配方；状态变化也要检查机器已缓存配方、并行和已启动作业如何处理，避免扣料后丢失。已启动作业的具体处理须原型验证后明确。

配方注册通常发生在世界加载之前且为进程级全局状态，不能直接假设世界加载事件可安全改注册表：须先验证单人切换不同存档、专用服、远程客户端 NEI 同步与重新进入世界；不能把一个世界的快照泄漏到另一个世界。候选方案是固定配方包装/展示代理加服务端执行守卫，世界加载后生成展示快照；若需要修改全局表，必须证明清理和重建完整并可同步。禁止只依靠可复制物品表示凭证。客户端 NEI 的静态展示与服务端当前拒绝之间的暂时差异是此重启方案的明确取舍，应在 GUI/提示中解释，重启后须一致。

原稿所称 UHV 两条配方及 UMV/UXV 的全部来源尚未由本次源码搜索证实。实现前必须从目标版本完整枚举真实输出、注册来源、元数据、替代配方、缓存与执行入口，审核工作台、组装机、多方块/代理机器及其他可执行方式；固定目标须带指纹并在缺失或不匹配时醒目报错、安全阻断受控生产，不能仅靠删除某两条配方就声称无法绕过。纯输出拦截还需排除已有物品和无关配方，不得误删玩家存货。

## 8. 分阶段交付和验证

1. 先核验版本与高风险原型：确认 AE2 上下文、配方生命周期和所有外壳路径；不满足基本权限时不发布玩法闭环。
2. 实现纯协议模型、版本化持久化、配置开关和受限管理员命令；测试两类债务、覆盖、溢出、里程碑、终止、缺失物品和跨世界隔离。管理员修改应受权限控制、写审计日志，危险重置需明确确认和备份。
3. 实现标记与便携终端，测试 900 上限、NBT、部分交付和恶意/过期请求；再实现手动清算与里程碑 GUI。
4. 实现并验证外壳守卫、静态展示和重启语义；分别覆盖新债务、清零、重启、跨世界、缓存配方及多人操作。
5. 实现 AE2 元件与网络刷新，再实现单项及批量清算、事件检测和待返还恢复；覆盖模拟、真实、普通存储混合、断网、卸载和重启。
6. 建立单元与集成测试；每阶段完成构建和静态检查，游戏启动及实际内容由用户在测试存档验证。先做独立安装、与主模组共存、客户端/专用服配置一致和断电恢复的测试，再考虑正式存档。

待产品决定：分类缓存与配置覆盖优先顺序；UMV 里程碑前置条件；已运行受控机器在新增债务时的处理；物品获取途径及终端/元件配方；FRP 关闭或缺失时对已有存档的具体运维规则。以上不应由实现细节悄然决定。
